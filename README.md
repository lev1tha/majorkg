# MAJOR KG — турнирная платформа по CS2

Киберспортивная платформа с индивидуальной регистрацией: игрок заявляется
один, составы собирает жеребьевка, сетка — верхняя, на выбывание.

Репозиторий разделен на два независимых приложения:

```
majorkg/
├── frontend/   Next.js 16 · App Router · Tailwind v4 · публичная часть и админка
└── backend/    Express 5 · TypeScript · SQLite · REST API, авторизация, вся логика
```

## Запуск

```bash
npm install
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env.local
npm run seed      # демо-данные: игроки, турниры, заявки, сетка, FAQ, учетка админа
npm run dev       # backend :4000 + frontend :3000
```

Сайт — http://localhost:3000, админка — http://localhost:3000/admin,
API — http://localhost:4000/api.

**Вход в админку** — логин и пароль, без Steam. Первая учетка создается
сидом: логин из `ADMIN_LOGIN` (по умолчанию `admin`), пароль из
`ADMIN_PASSWORD`. Если пароль в `.env` не задан, сид сгенерирует его и
напечатает один раз — дефолтного пароля в репозитории нет.

Отдельные процессы: `npm run dev:api`, `npm run dev:web`.

```bash
npm run build      # сборка обоих приложений
npm run typecheck  # проверка типов
npm run seed -- --reset     # пересоздать демо-данные с нуля
npm run seed -- --minimal   # боевой запуск: только учетка админа и FAQ
```

**На живом сайте запускайте `--minimal`.** Обычный сид заводит 40 демо-игроков
и 7 демо-турниров — вычищать их потом придется руками.

## Модель предметной области

Четыре решения определяют всё остальное.

**Дисциплина одна — CS2.** Поля `game` нет ни в схеме, ни в API, ни в
фильтрах. Убирать мультидисциплинарность пришлось из десятка мест, зато
интерфейс перестал спрашивать то, на что есть один ответ.

**Регистрация индивидуальная.** В турнир заявляется игрок, а не команда.
Пользовательских команд на платформе нет — их нельзя создать, потому что
они ничего не решают: состав всё равно соберет жеребьевка.

**Составы собирает жеребьевка** (`backend/src/services/lineups.ts`). Пул
делится на пять рейтинговых поясов FACEIT, каждый состав получает по
одному игроку из каждого пояса. Рядом с игроком на 3000 ELO гарантированно
окажутся партнеры уровнем ниже, а средний рейтинг составов сходится — на
демо-данных разброс держится в пределах 80 ELO. Подбор детерминирован:
одинаковый seed даёт одинаковый расклад.

**Сетка только верхняя** (`backend/src/services/bracket.ts`). Single
elimination: проигравший выбывает сразу, нижней сетки и гранд-финала нет.
Число составов округляется вверх до степени двойки, лишние места
становятся проходом без игры. Посев классический: 1 против последнего, 2
против предпоследнего. Победитель проводится в следующий раунд сразу при
сохранении протокола.

Призовых фондов, балансов и трансляций в системе нет — ни колонок в базе,
ни полей в API, ни блоков в интерфейсе. Деньги фигурируют ровно в одном
месте: организационный взнос за участие (`entry_fee`, по умолчанию 500
сом). Он задается на турнир, виден игроку до подтверждения заявки и
суммируется в обзоре админки как ожидаемые поступления.

**Тексты живут в базе, а не в коде.** Регламент турнира и FAQ редактируются
организатором: и то и другое попадает в разметку для поиска, поэтому
менять их пересборкой фронтенда было бы неудобно и медленно.

## Backend

Express 5 + TypeScript + SQLite (`better-sqlite3`) + zod. Никаких внешних
сервисов: база — файл, поднимается сама при первом запуске.

```
backend/src/
├── db/         схема (schema.sql), подключение, сиды
├── lib/        HTTP-хелперы, сессии, адаптеры Steam и FACEIT
├── middleware/ аутентификация, обработка ошибок, rate limit
├── services/   вся бизнес-логика: турниры, заявки, жеребьевка, сетка, матчи
├── routes/     тонкие хендлеры: валидация zod + вызов сервиса
└── types.ts    контракт API (зеркалится во frontend/src/lib/types.ts)
```

### Основные маршруты

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `GET` | `/api/tournaments` | Каталог с фильтрами и пагинацией |
| `GET` | `/api/tournaments/:slug` | Турнир + статус заявки текущего игрока |
| `GET` | `/api/tournaments/:slug/participants` | Заявленные игроки |
| `GET` | `/api/tournaments/:slug/lineups` | Составы после жеребьевки |
| `GET` | `/api/tournaments/:slug/bracket` | Верхняя сетка по раундам |
| `POST` · `DELETE` | `/api/tournaments/:slug/register` | Индивидуальная заявка и отзыв |
| `POST` | `/api/tournaments/:slug/checkin` | Подтверждение готовности |
| `GET` | `/api/players` · `/api/players/:nickname` | Игроки и профиль |
| `GET` | `/api/leaderboard` | Рейтинг сезона — только игроки |
| `GET` | `/api/matches` · `/api/matches/:id` | Матчи и протоколы |
| `POST` | `/api/matches/:id/appeals` | Апелляция от участника матча |
| `GET` · `POST` | `/api/matches/:id/veto` | Вето карт: состояние и ход участника |
| `GET` | `/api/faq` | Опубликованные вопросы и ответы |
| `POST` | `/api/auth/me/sync` | Подтянуть Steam и FACEIT для себя |
| `POST` | `/api/admin/auth/login` · `/logout` | Вход организатора по логину и паролю |
| `GET` · `POST` · `DELETE` | `/api/notes/...` | Личные скаут-заметки |
| `GET` | `/api/auth/steam` → `/api/auth/steam/callback` | Вход через Steam |
| `GET` | `/api/auth/me` | Текущий пользователь |

Админские маршруты под `/api/admin/*` требуют сессии организатора:
модерация заявок и игроков, конструктор турниров, `POST .../draw`
(жеребьевка), `POST .../bracket` (построение сетки), редактор FAQ, ввод
протоколов и разбор апелляций.

Ключевой для судейства маршрут — `PATCH /api/admin/matches/:id/winner`:
одно действие закрывает матч и проводит победителя в следующий раунд.
Счет по картам при этом не обязателен, серия записывается как 1:0;
подробный протокол вводится отдельно через `.../score`.

### Авторизация

На платформе две независимые роли и две cookie.

**Игрок** входит через Steam по OpenID 2.0 — официальный механизм Valve,
API-ключ для самого входа не нужен. Ответ Steam проверяется повторным
запросом `check_authentication`: `claimed_id` из редиректа — утверждение
клиента, а не доказательство.

После входа игрок синхронизируется с двумя источниками, оба по одному
ключу — SteamID64:

- **Steam** (`STEAM_API_KEY`) — ник и аватар;
- **FACEIT** (`FACEIT_API_KEY`) — рейтинг, уровень и пожизненная
  статистика (K/D, хедшоты, winrate, матчи).

Профиль FACEIT ищется по `game_player_id`, то есть по тому же SteamID64:
FACEIT хранит его в `games.cs2`. Поэтому привязка автоматическая — поля
«введите свой ник на FACEIT» на платформе нет и не нужно. Синхронизация
идет в фоне (игрок не ждет два внешних API на редиректе) и не чаще раза
в час: у FACEIT есть лимит запросов, упереться в него значит потерять
данные для всех.

Без ключей вход работает, но ник выглядит как `steam_XXXXXX`, аватара
нет, а рейтинг остается снимком из базы — интерфейс честно пишет об этом
в профиле и дает кнопку «Обновить».

**Организатор** входит по логину и паролю (`/admin`). Судейство — это
работа, а не игровой аккаунт: организатор может вообще не играть в CS2.
Пароль хранится как scrypt-хеш с индивидуальной солью, сессия живет
12 часов, на форму входа стоит лимит в 10 попыток в минуту, а ответ на
неизвестный логин и на неверный пароль одинаковый — иначе форма
подсказывала бы, какие логины существуют.

Отдельного маршрута `/admin/login` нет: без сессии любой `/admin/*`
показывает форму, после входа человек остается там, куда шел.

### Рабочий цикл организатора

Статус турнира — не подпись, а рубильник: он открывает заявки, закрывает
их и завершает турнир. Отсюда и порядок работы в карточке турнира:

1. **Черновик** → заполнить поля, регламент, пул карт.
2. **Регистрация** → турнир виден на сайте, игроки заявляются.
3. Подтвердить заявки — жеребьевка берет только подтвержденные и
   прошедших check-in, поэтому неподтвержденный игрок просто не попадет
   в составы. В таблице есть «Подтвердить все».
4. **Check-in** → заявки закрыты, идет подтверждение готовности.
5. **Жеребьевка** → составы по рейтинговым поясам. **Сетка** → верхняя
   сетка по посеву. Повторная жеребьевка стирает текущую сетку.
6. **Идет** → в разделе «Сетка» кликом по матчу отмечается победитель,
   он сразу встает в следующий раунд.
7. **Завершен** → итоги зафиксированы.

### Вето карт

До вето организатор не знает, какие карты готовить на сервере, а команды
— во что играют. Раньше это решалось перепиской; теперь порядок задан
правилом и виден обеим сторонам (`backend/src/services/veto.ts`).

В базе лежат только сделанные ходы. План — кто банит, кто пикает и в
каком порядке — выводится из формата серии и размера пула: правило
однозначное, дублировать его в таблице незачем. Для семи карт выходит
классика CS2: BO1 — шесть банов и решающая, BO3 — ban-ban-pick-pick-ban-ban
и решающая, BO5 — два бана, четыре пика и решающая.

Первым ходит сторона с лучшим посевом. Это не жребий: посев уже заработан
средним рейтингом состава, и право первого бана — его следствие.

Ходят участники матча, каждый за свою сторону; доска у ожидающей стороны
обновляется сама. Организатор может сходить за любую сторону, если состав
не выходит на связь, и сбросить вето. Когда вето закончено, порядок карт
уходит в протокол матча — судье не нужно вводить их заново — и попадает в
раздел **Серверы**, где видно, что готовить прямо сейчас.

### Миграции

`schema.sql` состоит из `CREATE TABLE IF NOT EXISTS`: на пустой базе он
создает всё, но на работающей пропускает таблицу целиком — новые колонки
не появятся. Для боевой базы этого мало, поэтому после схемы идет шаг
догоняющих миграций (`backend/src/db/migrate.ts`): он сверяет фактические
колонки с ожидаемыми и добавляет недостающие. Добавили поле в схему —
допишите его и туда.

### Начисление очков

Очки сезона — единственный рейтинг платформы: 25 за выигранную карту,
100 за выигранную серию. Начисляются при сохранении протокола. Повторный
ввод счёта (после апелляции) сначала снимает прежние очки, поэтому
пересчёт не задваивает награду.

## Frontend

Next.js 16 App Router. Своих данных не держит: server components ходят в
API через `src/lib/api.ts`, браузерные мутации — через
`src/lib/api-client.ts`.

Запросы из браузера идут на относительный `/api/*`, который Next.js
проксирует в бэкенд (`rewrites` в `next.config.mjs`). Благодаря этому
cookie сессии остается same-origin и CORS в проде не нужен. Server
components обращаются к бэкенду напрямую по `API_INTERNAL_URL` — на один
сетевой хоп меньше.

### Заметки по реализации

**Сетка** (`components/tournament/bracket*.tsx`). Раунды — колонки с
равными flex-слотами, поэтому центры матчей следующего раунда попадают
ровно в середину пары предыдущего; соединители рисуются псевдоэлементами,
без пересчета координат в JS.

**Переключение экранов без `AnimatePresence`.** Там, где действие
заканчивается `router.refresh()` (заявка, жеребьевка), exit-анимация не
переживает обновление серверного дерева: framer-motion обрывает её на
середине и оставляет уходящий блок на экране. Анимируется только
появление.

**Анимации входа — на CSS, не на JS.** Блок, который стартует с
`opacity: 0` и полагается на requestAnimationFrame, остается невидимым,
если кадры притормозят. Для героя это означало бы пустую главную, поэтому
там `@keyframes` с `fill-mode: both` — он всегда доходит до конечного
состояния и уважает `prefers-reduced-motion`.

**Даты без `Intl`.** Node и браузер расходятся в разделителях, а
расхождение ломает гидрацию. Сдвиг в UTC+6 считается вручную
(`lib/utils.ts`), поэтому результат одинаков на сервере и клиенте.

**Скаут-заметки** (`components/scouting/scout-notes.tsx`) хранятся на
бэкенде и видны только автору — это личная разведка перед матчем, а не
публичный комментарий.

## Интеграции

**Steam** — OpenID 2.0, ключ нужен только для подтягивания ника и
аватара (`STEAM_API_KEY`).

**FACEIT** — Data API v4 (`FACEIT_API_KEY`). Без ключа интерфейс честно
показывает снимок рейтингов из базы, а не живое ELO; подпись под
таблицами об этом сообщает. С ключом ELO подтягивается при открытии
профиля и сохраняется.

Переменные окружения — `backend/.env.example` и `frontend/.env.example`.

## Деплой

Фронтенд и бэкенд разворачиваются независимо.

**Backend** — любой хост с Node 22+: `npm run build --workspace backend`,
затем `npm start`. Для продакшена обязательны `SESSION_SECRET`, `SITE_URL`,
`API_URL` и `CORS_ORIGINS`. SQLite-файл должен лежать на постоянном диске;
для перехода на Postgres достаточно заменить слой `backend/src/db`.

**Frontend** — Vercel или любой Node-хост:

```bash
cd frontend && npx vercel --prod
```

В переменных проекта задать `NEXT_PUBLIC_SITE_URL` и `API_INTERNAL_URL`
(публичный адрес бэкенда).
